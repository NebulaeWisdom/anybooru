# e621ng 客户端用法

`E621` 是与 `Danbooru` / `Moebooru` / `Serika` 并列的第四个客户端，访问运行 e621ng 引擎的站点：
e621.net 与其安全内容镜像 e926.net 是同一引擎的两套部署，同一份代码、同一套路由，站点名或显式 URL 决定连哪一套。

```python
from pybooru import E621
with E621('e621') as client:                                  # 读包内默认 pybooru.json
    posts = client.post_list(**client.config['examples']['e621']['post_query'])
    print(posts[0]['id'], posts[0]['rating'], posts[0]['file']['ext'])
```

按配置里的样例查询（`rating:s`、`limit=2`），从真实响应提取的首帖字段值为：

```text
6709455 s jpg
```

e926 示例返回同一个首帖；实际命令、逐调用 URL 与响应摘要见 [verification.md](verification.md)。

e621ng 与 Danbooru 同样是 Rails 引擎、同样用 HTTP Basic、同样有复数 `GET /posts.json`，但**不是同一套契约**：
帖子负载结构、评级词表与计数路由都不同，选类由调用者决定，库不做引擎识别也不会失败后换类重试。
本页只讲“这个类怎么用”；18 个方法的签名与返回形态见 [方法参考](e621-api.md)，按目的找入口见
[能力入口](e621-capabilities.md)，上游依据与排除项见 [契约审计附注](e621-contract-notes.md)。

## 构造

```python
E621(site_name=None, site_url=None, username=None, api_key=None, proxies=None,
     *, config_file=None, timeout=None, user_agent=None)
```

`site_name` 是配置 `sites` 段的键名（默认配置里有 `'e621'` 与 `'e926'`），同时决定读取哪个站点的
`username` / `api_key`；`site_url` 显式覆盖地址（自托管或未列入样例清单的实例用这个，库没有地址后备）；
`config_file` 默认 `None`，即读随包安装的 `pybooru/pybooru.json`（`pybooru.DEFAULT_CONFIG_FILE`），
显式传路径才读别的文件，指到的文件不存在直接抛 `FileNotFoundError`，不回落默认文件或内置站点；
其余参数显式覆盖配置 `request` 段的同名值。站点条目与 Danbooru 同构（`url` / `username` / `api_key`），
没有 `password`、`hash_string` 或路径版本开关，见 [configuration.md](configuration.md)。

解析后的配置挂在公开属性 `config` 上：`config['request']['timeout']`（`30`）、
`config['sites']['e621']['url']`、`config['examples']['e621']['post_query']`；
示例脚本都从 `config['examples']['e621']` 取站点、查询与调用间隔，切换站点只要把 `'e621'` 换成 `'e926'`
或传 `site_url`。

## 认证

`username` 或 `api_key` **任一非空**就附加 HTTP Basic（缺项按空串补），两项都空才匿名；权限由服务端判定，
客户端不预判、不在认证失败后退回匿名。上游把 Basic 凭据按第一个 `:` 切成 `login` 与 `api_key` 校验；
上游同时接受 `login` + `api_key` 请求参数，那条路径额外要求同源请求，本库**只走 Basic 头**。
两个相关标签方法的成员成功路径仅源码对齐、未实测，详见
[authentication.md](authentication.md#e621ng-系站点)。

## 通用请求入口

`request(method, path, *, params=None, data=None, files=None, envelope=None)` 是所有原生方法的底座，
18 个原生方法之外的上游 JSON 路由也直接用它：

```python
from pybooru import E621

with E621('e621') as client:
    query = client.config['verification']['e621']['post_query']     # {"tags": "rating:s", "limit": 1}
    # 原生方法用的同一条路由，通用入口不拆信封，返回上游原样的 {"posts": [...]}
    body = client.request('GET', 'posts', params=query)
    print(list(body), body['posts'][0]['id'], client.last_call['status_code'])
```

从真实匿名响应与 `last_call` 提取的值（2026-09-15）：

```text
['posts'] 6709455 200
```

* `method` 是 `'GET'` / `'POST'` / `'PUT'` / `'DELETE'` 等；`path` 带不带 `.json` 都可以（自动补，
  `'posts/random'` 与 `'posts/random.json'` 等价），开头的 `/` 会去掉；`params` 是查询参数（Rails 括号形式），
  `data` 是请求体，`files` 非空时改用 multipart 表单；
* **路径里的 ID 要调用者自己转义**：原生方法已内置转义（标签名、画师名、wiki 标题都按整段 `quote`，
  所以 `wiki_page_show('help:api')` 发成 `wiki_pages/help%3Aapi.json`），裸路径由调用者负责；
* **`envelope` 是显式契约**：它只接受一个键名，方法按上游请求分支决定拆哪个键，缺键直接 `KeyError`，
  不会去找别的形状；所以“为什么这里要传 envelope/这里为什么没拆”都能从上游分支反推（见下一节）；
* **不做隐式兜底**：不自动重试、不自动翻页、不替调用者补参数，网络错误、限流、5xx 全抛给调用者；
* **请求头固定**：`User-Agent` 取配置，`Accept: application/json`；会话 `trust_env=False`，
  代理只来自配置或显式参数，不读环境变量。

## 参数编码

查询串与表单共用一套 Rails 编码：嵌套 dict → `a[b]`，列表 → 重复键 `a[]`，布尔 → 小写 `true`/`false`，
`None` 不发送。因此搜索字典要整包交给方法的 `search` 参数：

```python
with E621('e621') as client:
    example = client.config['examples']['e621']
    tags = client.tag_list(**example['tag_query'])
    matching = client.tag_list(search={'name_matches': tags[0]['name']},
                               **example['tag_query'])
```

**帖子路由是例外**：`posts#index` / `posts#count` / `posts#random` 不接受 `search` 字典，过滤条件全部写成
顶层 `tags` 元标签：

```python
with E621('e621') as client:
    example = client.config['examples']['e621']
    posts = client.post_list(**example['post_query'])
    count = client.post_count(tags=example['post_query']['tags'])
```

`page` 与 `limit` 是顶层参数，服务端自己分页与钳位：`page` 收纯数字页码，或游标 `b<id>`（取 id 小于该值、
即更旧的记录）与 `a<id>`（取 id 大于该值、即更新的记录），两种游标都按 id 逆序返回；`limit` 收 `0..320`
（缺省 `75`，帖子走账号的每页设置）；非法页码或超限返回 `410`。分页语义与 Danbooru 系站点同理，见
[pagination.md](pagination.md)。

## 返回值与信封

原生方法返回**上游 JSON 拆掉信封后的结果**，拆不拆、拆哪个键由上游请求分支决定，客户端不做形状猜测：

| 调用 | 返回 |
| :--- | :--- |
| `post_list()` 默认 | legacy 帖子数组（上游 `{"posts": [...]}` 的 `posts`） |
| `post_show(...)` / `post_random(...)` 默认 | 单个 legacy 帖子（上游 `{"post": {...}}` 的 `post`） |
| `post_list(md5=<32 位 md5>)` | 单个帖子（上游 `{"post": {...}}` 的 `post`），未命中 `404` |
| `post_list(only=...)` / `post_show(..., only=...)` | **不拆**：`only` 是非空值时上游直接输出裸数组/裸对象（`only=` 空串不算），方法原样返回 |
| `post_list(v2=True)` / `post_show(..., v2=True)` / `post_random(..., v2=True)` | **不拆**：v2 蓝图本来就不带信封，返回裸数组/裸对象 |
| `post_count()` | `{'count': N, 'capped': bool}`（上游内联对象，无信封） |
| `tag_list` / `artist_list` / `comment_list` / `pool_list` / `note_list` / `wiki_page_list` | 上游数组原样（`tag` / `artist` / `comment` / `pool` / `note` / `wiki_page` 对象） |
| `tag_show` / `artist_show` / `comment_show` / `pool_show` / `note_show` / `wiki_page_show` | 上游对象原样 |
| `related_tag` / `related_tag_bulk` | 上游数组 / 以标签名为键的对象（成员权限，匿名 `403`） |
| 空成功正文（未指定 `envelope`） | `None`；非 2xx 一律抛 `PybooruHTTPError`（带状态码、URL、正文） |

`last_call` 记录每次请求的实际情况，`url` 是含查询串的最终地址，可直接核对“参数到底发成了什么样”：

```python
with E621('e621') as client:
    client.post_list(**client.config['examples']['e621']['post_query'])
    print(client.last_call['status_code'], client.last_call['url'])
# 本轮对应值：200 https://e621.net/posts.json?tags=rating%3As&limit=2
```

## 常见坑

1. **评级词表是 `s` / `q` / `e`**：`rating:g` 这类值会被上游**静默丢弃**（与不传标签、与非法元标签结果完全相同，
   都不报错），所以复制 Danbooru 的查询会得到“没过滤”的结果而不是报错；`rating:safe` / `questionable` /
   `explicit` 因上游取首字母判断而合法。e926 那类安全内容站点的实际过滤来自该站部署配置，不在上游仓库默认值里。
2. **帖子负载是嵌套结构**：`file` / `preview` / `sample` / `score` / `tags` 各自是对象，
   `tags` 是九个类别（`general`、`artist`、`contributor`、`copyright`、`character`、`species`、`invalid`、
   `meta`、`lore`）到标签名数组的字典；**没有** `tag_string`、`file_url`、`media_asset` 这些 Danbooru 字段，
   按 Danbooru 写法取字段会 `KeyError`。
3. **不可见的帖子不会删键，而是把媒体 URL 置空**：`file.url`、`preview.url` / `preview.alt`、
   `sample.url` / `sample.alt` 只在帖子对当前身份可见时才有值，否则保持 `null`；`file.md5` / `file.ext`
   由蓝图直接取自模型（模型的默认序列化才会隐藏这两个键），两条路径的差别见
   [附注](e621-contract-notes.md#sec-post-shapes)。
4. **`only=` 不是字段筛选**：只要它非空，上游就去掉 `posts`/`post` 信封，返回的仍是**完整** legacy 负载；
   想换负载形状要用 `v2=True`（新蓝图：`files` / `stats`，`tags` 是数组或按类别分组的字典）。
5. **顶层 `random=True` 不是随机排序**：它只影响上游 `PostSets::Post` 的随机状态与呈现，查询本身不变；
   随机排序要用 `tags='order:random'` 元标签，或直接用 `post_random`。
6. **空的 `search` 值会被重定向**：上游对所有 `GET`/`HEAD` 请求会剔除空白 `search` 项并 `302` 到清理后的地址；
   客户端把 `None` 直接省略，但 `''` 会照发并触发重定向。
7. **`comment_list` 不等于“全部评论”**：匿名看不到被隐藏的评论、看不到评论被关闭的帖子的评论，
   未给 `search={'id': ...}` 时还会再套一层评分阈值过滤；`group_by='post'` 返回的是**裸帖子对象**，
   既不是评论蓝图也不带评论内容。返回字段随身份变化，见 [能力入口](e621-capabilities.md)。
8. **计数是封顶值**：`post_count` 背后是分页上限计算出的上界，命中上限时 `capped=True`、`count` 只是下限
   （实测 `240001` / `capped=True`）。不要改找 Danbooru 的 `/counts/posts.json`：e621ng 没有该路由。
9. **`related_tag` 两条路径都是成员权限**：匿名请求 `403`（`{"success": false, "reason": "Access Denied"}`），
   而且参数层级不同——`related_tag` 用 `search={'query': ..., 'category_id': ...}`，
   `related_tag_bulk(query, category_id=None)` 用顶层参数。
10. **`/help/api` 不是本方法的对象**：`wiki_page_show('help:api')` 请求的是
    `/wiki_pages/help%3Aapi.json`，返回 WikiPage；站点上的 `/help/api` 是 `help_pages` 路由下的另一种记录
    （HelpPage），本库不为它提供原生方法，需要时用 `request()`。

命名规则：`xxx_list` 列表/搜索（`search` + `**params`），`xxx_show` 单条详情；本家族**没有原生写方法**，
写路由需要时用 `request()` 显式调用。

## 可运行示例

三个脚本都支持 `--config` 与 `--site`，`--config` 省略即读包内默认配置，站点名来自
`examples.e621.site`；查询、条数与调用间隔全部来自配置文件，脚本只调用匿名可达路径：

```bash
.venv/Scripts/python.exe examples/e621/list_posts.py --site e621
.venv/Scripts/python.exe examples/e621/browse_resources.py --site e621
.venv/Scripts/python.exe examples/e621/wiki_pages.py --site e621
```

* `list_posts.py`：`post_list`（取得 `rating:s` 的前两帖：`6709455`、`6709449`）→ 取首帖 id 调 `post_show`
  → `post_random`（返回 `1434546`），展示 legacy 负载的嵌套结构与三个帖子方法的信封差异。
* `browse_resources.py`：标签列表 → 标签详情、画师列表 → 画师详情、评论列表 → 评论详情、合集列表 → 合集详情、
  笔记列表 → 笔记详情；只打印身份字段，评论与笔记正文只报长度。
* `wiki_pages.py`：wiki 列表 → 按配置里的标题 `help:api` 取单个页面（`id 11224`），展示标题里的冒号被转义。

以 `--site e926` 再跑一遍即可换到安全内容站点。六次运行、30 次调用全部 `HTTP 200` 且退出码 `0`；
命令与逐调用摘要见 [verification.md](verification.md)。

## 边界与未实测

* 18 个方法里 16 个有匿名成功记录（15 个来自示例、两个站点各跑一遍，外加两个站点的 `post_count`）；
  `related_tag` 另有匿名 `403` 记录（累计 17 个方法被调用过），`related_tag_bulk` **没有任何线上调用**。
  两者的成员成功路径需要凭据，未实测。
* 返回形态复核覆盖：两个站点的 `post_count`、原始 `posts` 信封、`md5` 单帖分支、`only` 拆信封分支、
  `v2=true` 新蓝图分支。参数组合、身份差异与写路径均未实测。
* e621ng 面**没有原生写方法、没有管理/审核方法、没有浏览器 HTML 页面方法**；上游写路由与其它只读 JSON 路由
  需要用 `request()` 显式调用，排除清单见 [能力入口](e621-capabilities.md)。
* e926 的可见范围由该站部署决定，不能从上游仓库默认值断言；逐条状态以
  [verification.md](verification.md) 与[契约审计附注](e621-contract-notes.md)为准。

示例或非 `with` 方式用完记得 `client.close()`。
